- 방법: 페이지·워커의 `fetch`를 감싸 URL·메서드·본문 크기·"원문 조각(발화 앞 24자) 포함 여부"를 기록. transformers.js는 import 시 fetch를 `env.fetch`로 잡아두므로 감싼 뒤 다시 주입. fetch로 안 잡히는 로드는 워커의 리소스 타이밍으로 보완(본문 없음).
- 캐시 비운 상태 전체 분석(실제 파일): 요청 10건 = huggingface.co 7(config·tokenizer·model_quantized.onnx, 전부 GET 본문 0) + cdn.jsdelivr.net 2(ORT wasm) + localhost 1(파일). 분석 워커 0건. **본문 있는 요청 0, 원문 포함 0 → 통과.** 캐시된 상태에선 요청 1건(파일)뿐.
- 양성 대조: 페이지에서 발화 텍스트를 POST하면 "원문 포함 1건 → 실패"로 잡히고, 숫자만 담은 POST는 잡히지 않음. 검사가 비어 있지 않음을 확인.
- 한계: 프로덕션 빌드·서버 동기화가 생기면 집계 전송 요청이 추가되므로 그때 본문에 원문 조각이 없는지 같은 패널로 재검증. 개발자 도구 네트워크 탭 전수 확인은 11/24 주에 별도.

## 2026-11-10 정적 임베딩 비교군 (static-e5-0.1.0)
- 만든 법: `eval/static/distill.mjs` — e5-small 어휘 250,002개 중 한글·라틴·숫자·구두점 토큰 120,662개를 각각 모델에 통과(59초) → 평균 제거 → PCA 128차원 → Zipf 가중(어휘 id 순위) → 행별 int8. 표 14.7MB + 스케일 0.5MB + id 0.8MB = **약 16MB**(e5 q8 113MB+토크나이저 16MB 대비 1/8). 추론 없이 토크나이저 + 표 조회 + 평균.
- 속도(실제 발화 100개, 평균 71자, 내장 브라우저 wasm): **static 0.6ms/개** vs e5-small 69.5ms/개 (약 115배). 로드 665ms(표 16MB) vs 1,368ms.
- 합성 개발셋 반복 탐지(같은 조건): static 최고 F1 **.44**(P .50 R .40, 같은 대화 p90) vs e5 .67. 바꿔 말한 반복(paraphrase)을 거의 못 잡고(유사도 분포가 넓어 -0.4~0.6), 같은 형식 새 내용은 오탐. 어순·문맥을 못 보는 정적 임베딩의 한계가 그대로 드러남.
- 결론: 속도·용량 비교군으로 논문 표에 넣는다. 서비스 기본값은 e5-small 유지. 과업 분류 비교(A/B/C)는 라벨 후 `run_abc.mjs static-e5`로.
