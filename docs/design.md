# 설계 문서

과제: relog (생성형 AI 대화의 반복·비효율 패턴 온디바이스 탐지 및 개인화 활용 전략 추천·평가)
최종 갱신: 2026-11-11. 요구사항은 [requirements.md](requirements.md), 실측은 [measurements.md](measurements.md), 파일 구조 실측은 [export-format.md](export-format.md).

## 1. 구성

```
사용자 브라우저 (React + TypeScript)                         서버 (Spring Boot + MySQL, 선택)
┌──────────────────────────────────────────────┐            ┌─────────────────────────────┐
│ 내보내기 zip                                   │            │ 서비스 계정                   │
│  └ 분석 워커: 해제 → 파서 → 정규화             │  집계 숫자  │ 주별 집계 스냅샷              │
│  └ 임베딩 워커: 임베딩 → 분류 → 탐지           │ ─────────▶ │ 추천 엔진(규칙) · 추천 이력    │
│ 발화 대장 → 주 단위 집계 (IndexedDB, 동의 시)   │  추천·추이  │ 피드백 · 변화 추이            │
│ 추천(로컬 규칙) · 리포트 · 뷰어                │ ◀───────── │ 기능 카탈로그                 │
└──────────────────────────────────────────────┘            └─────────────────────────────┘
        원문·임베딩은 이 영역을 벗어나지 않음
```

- 분석 엔진은 전부 브라우저에서 돈다. 서버 없이도 진단·탐지·추천·변화 비교가 된다(로컬 전용 모드, GitHub Pages 배포판).
- 서버 동기화는 사용자가 서비스 계정으로 로그인해 "집계 보내기"를 눌렀을 때만 일어난다. 그때 추천과 변화 추이는 서버가 계산한 값으로 바뀐다.

## 2. 모듈

| 모듈 | 위치 | 설계 요점 |
|---|---|---|
| 분석 워커 | web/src/worker/analyze.worker.ts | 파일을 8MB 조각으로 읽어 fflate 스트리밍 해제. zip 여러 개 병합. 항목별로 파서에 넘겨 zip 전체를 메모리에 올리지 않는다. |
| 파서 | web/src/parser/ | chatgpt.ts(mapping + current_node 활성 경로), claude.ts(chat_messages 트리), claudeCode.ts(세션 .jsonl). 공통 출력은 Conversation(id, platform, client, turns, toolNames, pluginNames). 필드가 빠진 대화는 오류로 기록하고 계속한다. |
| 정규화 | parser/normalize.ts | 코드 블록 → [CODE_BLOCK: 언어], 정보량 없는 메시지 제외(skipped), 짧고 문맥 의존(context_required), 토큰 근사. |
| 임베딩 | worker/embed.worker.ts | transformers.js(ONNX Runtime Web), multilingual-e5-small q8, "query:" 접두어, WebGPU 우선·WASM 기본. 분석이 끝나면 워커를 종료해 메모리를 돌려준다. 비교군 static-e5(정적 표). |
| 과업 분류 | classify/classifier.ts | 제품 기본은 B 유형별 중심점(예시 발화의 임베딩 합 + 라벨된 공개 표본의 유형별 임베딩 합, labeled-centroids.json). C k-NN(예시 발화)은 개발 패널에서 비교용. A(TF-IDF+선형)는 평가 스크립트에만 둔다. 비교 실험에서 Macro F1이 B·예시+학습 0.45, C·예시만 0.36이었다. Claude Code 세션 메시지는 코딩으로 고정하고 세션 단위 키워드로 코딩 세부를 나눈다(codingSub.ts). |
| 반복 탐지 | detect/detector.ts | 아래 3절. |
| 사용자 보정 | detect/corrections.ts | "반복 아님"으로 고친 메시지 id를 localStorage에 두고 등급을 뗀 결과를 화면·추천·집계에 쓴다. |
| 집계 | store/ledger.ts, store/db.ts | 발화 대장 키 = 대화 ID#메시지 ID#내용 해시. 메시지 생성일 기준 주 단위 집계, 대장에서 언제든 재계산. IndexedDB 보관은 동의했을 때만. |
| 추천 | recommend/recommend.ts, catalog/catalog.json | 필수 조건 필터(플랫폼·요금제·이미 사용) → 점수(문제 신호 가중치×2 + 대화 종류 가중치 + 우선순위/100 + 피드백) → 상위 3건, 종류당 최대 2건. 서버 RecommendEngine.java는 같은 규칙의 포팅이며 같은 테스트를 통과한다. |
| 리포트 | App.tsx | 요약 한 줄 + [다시 말한 지시][추천][변화]. 넓은 화면은 2열. 설명은 ? 아이콘. 상세 원문은 화면에만 표시. |
| 뷰어 | viewer/Viewer.tsx | ?view=1. 서버 보관 집계·최근 처방·변화만 열람. manifest로 홈 화면 추가 가능(내부 테스트용). |
| 서버 | server/ | Spring Boot 4.0.9, Java 21, Spring Security(Bearer 토큰, 세션 없음), JPA, MySQL 8(개발은 H2). |

## 3. 다시 말한 지시 탐지 (det-0.3.0)

1. 후보: 같은 대화에서 각 사용자 메시지와 그 앞 최근 10개 사용자 메시지의 코사인 유사도 최댓값.
2. 기준: 절대값이 아니라 그 사용자 데이터의 분포에서 정한다. 같은 대화 안 떨어진 쌍(2칸 이상) 유사도의 p90. 앱·Claude Code 묶음별로 따로 잰다. 쌍이 20개 미만이면 서로 다른 대화 무작위 쌍의 p99.
3. 구제: "아까 말했" 같은 반복 표지가 있는 지시는 서로 다른 대화 쌍 p90만 넘어도 후보.
4. 제외: 범용 문구(3개 이상 대화에 같은 문장, 또는 5자 이하), 몇 분 안 재전송, 지시문이 아님(질문형은 "비슷한 질문 다시 함"으로 따로 셈), 정기 작업 명령(글자까지 같은 지시, 커밋·배포·진행류 짧은 지시), 잡담, 첨부 동반, 하루 넘게 지난 재방문(표지 없음), 사용자 보정.
5. 등급: 약함 = 기준 통과 + 지시문 + 제외 통과 / 가능성 있음 = 약함 + 24시간 이내 + 사이에 AI 답 / 확실함 = 가능성 있음 + 반복 표지.
6. 판정하지 않는 것: AI가 지시를 실제로 따랐는지. 후속 실험으로 분리한다.

계획서는 "유사도·표지·문맥·새 요구를 가중 점수로 결합"한다고 적었다. 실제 파일에서 e5 유사도가 0.84~0.95에 몰려 가중 합의 차이가 등급을 가르지 못했기 때문에, 같은 신호를 단계 규칙(기준 통과 → 제외 → 등급 조건)으로 바꿨다. 새 요구 표지는 점수에 쓰지 않는다.

평가: 합성 개발셋(40대화, 라벨 98) F1 0.67, 합성 테스트셋(52대화, 라벨 125) F1 0.43(정밀도 0.67, 재현율 0.31), 확실함 등급 정밀도는 두 셋 모두 1.00(5/5, 3/3). 바꿔 말한 반복은 대부분 기준 미만이라 건수가 실제보다 적게 잡힌다.

## 4. 데이터 경계

| 데이터 | 브라우저 메모리 | IndexedDB(동의 시) | 서버(동기화 시) |
|---|---|---|---|
| 대화 원문 | 분석 중에만 | 저장 안 함 | 보내지 않음 |
| 임베딩 | 분석 중에만 | 저장 안 함 | 보내지 않음 |
| 발화 대장(ID, 해시, 시각, 유형, 등급, 분량) | 있음 | 저장 | 보내지 않음 |
| 주별 집계 숫자 | 있음 | 대장에서 계산 | 보냄 |
| 요금제·쓰는 기능·피드백 | 있음 | localStorage | 보냄 |
| 서비스 계정(이메일, 비밀번호 해시) | - | 토큰만 localStorage | 저장 |
| ChatGPT·Claude 계정 정보 | 다루지 않음 | - | - |

- 서버 요청 본문의 문자열 필드는 플랫폼 이름과 분석 버전뿐이다(eval/test_parser.mjs의 "sync dto"에서 검사). 서버 DTO는 모르는 필드와 허용되지 않은 키를 거부한다.
- 개발자 패널(?dev=1)의 네트워크 감사가 페이지와 워커의 모든 요청을 기록하고, 요청 본문에 내 메시지 글귀가 들어 있는지 대조한다.

## 5. 서버 API

| 메서드 · 경로 | 내용 |

## 7. 버전

분석 버전 = 파서(export-0.3.0) · 정규화(norm-0.1.0) · 모델(multilingual-e5-small@q8/장치) · 분류기(cls-0.2.0+예시 버전+라벨 합 버전) · 탐지기(det-0.3.0) · 카탈로그(catalog-0.3.1) · 추천 규칙(rec-0.1.1). 앞의 다섯 개를 이은 것이 버전 키이며, 키가 다른 기간끼리는 비교하지 않는다.

## 8. 계획 대비 달라진 점

| 계획 | 현재 | 이유 |
|---|---|---|
| Spring Boot 3 | Spring Boot 4.0.9 | 프로젝트 생성 시점에 3.x 지원이 끝나 있었다 |
| 추천·변화 추이는 서버에서 | 기본은 브라우저, 동기화하면 서버 계산값 | 서버 없이도 쓸 수 있게(정적 배포). 서버 경로는 선택 기능으로 유지 |
| 탐지는 가중 점수 | 단계 규칙 + 분포 기준 | 3절 참고 |
| 대상은 ChatGPT 내보내기 | ChatGPT 파서는 합성 파일로만 확인, 실측은 Claude 앱·Claude Code | 실제 ChatGPT 파일 확보 뒤 검증 예정 |
| 분류 라벨은 공개 데이터 400건 | 표본 스크립트 준비(WildChat-1M 한국어), 라벨링 대기 | LMSYS는 접근 동의가 필요해 쓰지 않음 |
| 앱은 최소 뷰어 | 웹 뷰어(?view=1) + manifest | 스토어 출시는 후속 범위 |

## 9. 위험과 대응

- 내보내기 형식 변경: 어댑터 분리, 누락 필드 방어, 실제 파일 실측 기록(export-format.md).
- 모델 용량·속도: 실측 후 정적 임베딩으로 바꿀 수 있게 임베더를 분리.
- 탐지 오탐: 정밀도 우선(등급 분리, 제외 규칙), 사용자 "반복 아님" 보정.
- 카탈로그 노후화: 항목별 확인일 기록, 확인 안 된 항목은 추천에 내보내지 않음.
- 평가 참여자 부족: 탐색적 평가로 표기, 분류·탐지 정확도는 공개·합성 데이터로 따로 측정.
